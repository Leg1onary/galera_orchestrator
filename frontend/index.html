Playbooks

Node Down
  1. Проверить wsrep_cluster_size на живой ноде
  2. Если size=1 — кластер non-Primary
  3. Исправить сеть / поднять сервис
  4. Нода автоматически сделает IST
  5. Проверить wsrep_local_state_comment = Synced
Full Cluster Crash
  1. Найти ноду с наибольшим seqno в grastate.dat
  2. На ней выполнить galera_new_cluster
  3. Запустить mariadb.service на остальных нодах
  4. Дождаться IST/SST синхронизации
Split-Brain (2 ноды)
  1. Оба узла считают себя Primary
  2. Остановить MariaDB на одной ноде
  3. Проверить данные — выбрать "правильную" ноду
  4. Перезапустить отставшую через Rejoin

                    Управление сервисом MariaDB
                

                


                    

                        

                            
Start

                            Safe
                        

                        
Запустить сервис mariadb.service на выбранной ноде. Нода автоматически присоединяется к кластеру через IST (инкрементальный перенос состояния) если отставание небольшое, или через SST (полный снапшот) если нода отсутствовала долго.

                        
systemctl start mariadb.service

                    


                    

                        

                            
Stop MariaDB

                            Danger
                        

                        
Штатно остановить сервис mariadb.service на выбранной ноде. Нода корректно покидает кластер, wsrep_cluster_size уменьшается на 1. При 2 нодах без арбитра кластер теряет кворум и переходит в non-Primary — все новые записи блокируются.

                        
systemctl stop mariadb.service

                        
⚠ При 2 нодах без арбитра — остановка любой ноды блокирует запись в кластер.

                    


                    

                        

                            
Restart

                            Warning
                        

                        
Перезапустить сервис mariadb.service (Stop + Start). Используется для применения изменений конфигурации galera.cnf или my.cnf без перезагрузки ВМ. Нода временно выходит из кластера и автоматически переподключается.

                        
systemctl restart mariadb.service

                    


                    

                        

                            
Rejoin

                            Action
                        

                        
Переподключить ноду к работающему кластеру после кратковременного отказа или ручного вмешательства. Выполняет restart mariadb.service — нода заново проходит handshake с кластером и синхронизируется через IST или SST. Выбор метода (IST/SST) доступен из кнопки на карточке ноды в разделе «Дашборд».

                        
systemctl restart mariadb.service

                    


                    

                        

                            
R/O — Read Only

                            Warning
                        

                        
Перевести ноду в режим «только чтение» (read_only = ON). Используется при плановых работах или для исключения ноды из записи без остановки сервиса. Репликация Galera и мониторинг продолжают работать в штатном режиме. Текущий статус R/O отображается бейджиком на карточке ноды.

                        
SET GLOBAL read_only = ON;

                        
Нода остаётся в кластере и принимает репликацию, но отклоняет клиентские запросы на запись.

                    


                    

                        

                            
R/W — Read Write

                            Safe
                        

                        
Вернуть ноду в нормальный режим чтения/записи (read_only = OFF). Применяется после завершения плановых работ для включения ноды обратно в ротацию нагрузки. Бейджик R/O на карточке исчезает.

                        
SET GLOBAL read_only = OFF;

                    


                    

                        

                            
Ping (SSH)

                            Info
                        

                        
Проверить SSH-доступность ноды — отправляет тестовый SSH-запрос и измеряет время отклика. Позволяет убедиться что backend может подключиться к ноде перед выполнением команд. Выводит задержку в мс или сообщение об ошибке.

                        
ssh -o ConnectTimeout=5 user@host echo ok

                    


                    

                        

                            
Kill Query

                            Danger
                        

                        
Принудительно завершить зависший SQL-запрос на выбранной ноде. Доступно из раздела «Диагностика» → SHOW PROCESSLIST: для каждого активного запроса есть кнопка Kill. Полезно перед остановкой ноды чтобы избежать долгого ожидания завершения транзакций.

                        
KILL QUERY {thread_id};

                        
Kill Query завершает только запрос. Kill Connection закрывает всё соединение.

                    


                

            


            
            
            
            

                

                    
                    Recovery — Восстановление кластера
                

                


                    

                        

                            
Bootstrap Wizard

                            Danger
                        

                        
Пошаговый мастер восстановления кластера после полного отказа всех нод. 6 шагов с авто-переходами: 1) Pre-flight (MariaDB остановлена везде) → 2) wsrep-recover на всех нодах параллельно → авто-кандидат по максимальному seqno → 3) safe_to_bootstrap=1 → 4) galera_new_cluster → 5–N) последовательный запуск остальных нод с ожиданием Synced. Показывает таблицу seqno с подтверждением кандидата перед запуском.

                        
POST /api/bootstrap/wizard  {step: "check"|"recover"|"grastate"|"bootstrap"|"join"|"await_synced"}

                        
⚠ Все ноды должны быть остановлены перед запуском Wizard. Кандидат выбирается автоматически — можно подтвердить или прервать.

                    


                    

                        

                            
pc.bootstrap (non-Primary Fix)

                            Danger
                        

                        
Восстановить кворум без перезапуска MariaDB — для ситуации когда MariaDB работает, но кластер завис в состоянии non-Primary (например после split-brain когда связь восстановилась). Выполняет SQL-команду напрямую на работающей ноде.

                        
SET GLOBAL wsrep_provider_options = 'pc.bootstrap=YES';

                        
Применять только когда wsrep_cluster_status = «non-Primary» а сетевая связность восстановлена. Не использовать при реальном split-brain.

                    


                    

                        

                            
wsrep-recover-all (батч)

                            Danger
                        

                        
Запуск mysqld --wsrep-recover параллельно на всех нодах через SSH+ThreadPoolExecutor. Возвращает таблицу нода→seqno и автоматически определяет кандидата с наибольшим seqno. Используется как шаг 2 в Bootstrap Wizard и как отдельная кнопка в Recovery. MariaDB должна быть остановлена на всех нодах перед запуском.

                        
POST /api/wsrep-recover-all  →  {results:[{node_id, seqno}], candidate, candidate_seqno}

                        
Bootstrap Wizard автоматически использует кандидата. При ручном запуске — нода с наибольшим seqno выбирается для Bootstrap.

                    


                    

                        

                            
Сброс grastate.dat

                            Danger
                        

                        
Установить safe_to_bootstrap: 1 в файле /var/lib/mysql/grastate.dat на выбранной ноде через SSH. Необходимо при полном краше кластера когда у всех нод safe_to_bootstrap: 0 — без этого galera_new_cluster не запустится. Выполнять только на ноде с наибольшим seqno.

                        
sed -i 's/safe_to_bootstrap: 0/safe_to_bootstrap: 1/' /var/lib/mysql/grastate.dat

                        
⚠ Критическая операция. Выполнять только после определения ноды-кандидата через wsrep_recover.

                    


                    

                        

                            
Выбор донора SST

                            Warning
                        

                        
Принудительно указать какая нода будет донором при полной пересинхронизации (SST). По умолчанию Galera выбирает донора автоматически, что может перегрузить prod-ноду. Задаётся через SQL на ноде-получателе перед Rejoin с методом SST.

                        
SET GLOBAL wsrep_sst_donor = 'node-name';

                        
Значение действует до следующего рестарта MariaDB. Пустая строка = авто-выбор Galera.

                    


                    

                        

                            
IST vs SST (Rejoin)

                            Info
                        

                        
IST (Incremental State Transfer) — инкрементальная синхронизация: передаются только отсутствующие транзакции из gcache. Быстро, донор не нагружается. Работает если нода отсутствовала недолго и gcache донора не переполнен.

SST (State Snapshot Transfer) — полная копия датасета с донора. Медленно (зависит от размера БД), донор временно переходит в Donor/Desynced. Используется при долгом отсутствии ноды или повреждении данных.

                        
Метод выбирается в карточке ноды при нажатии «Rejoin» → выпадающий список IST/SST.

                    


                    

                        

                            
Maintenance Mode

                            Warning
                        

                        
Пошаговый мастер безопасного вывода ноды на техобслуживание без потери кворума. Последовательность: 1) R/O ON → 2) Ожидание recv_queue=0 → 3) Stop MariaDB → 4) [работы] → 5) Start MariaDB → 6) Ожидание Synced → 7) R/O OFF. Каждый шаг ожидает подтверждения состояния.

                        
Используйте Maintenance Mode при плановых работах на prod-кластере чтобы избежать потери записей.

                    


                    

                        

                            
Systemd Pre-check перед Bootstrap

                            Warning
                        

                        
Перед запуском galera_new_cluster бекенд автоматически проверяет через SSH: systemctl is-active mariadb.service на всех не-кандидатных нодах. Если MariaDB активна хотя бы на одной — Bootstrap блокируется с явным сообщением и списком нод, которые нужно остановить. Предотвращает split-brain при случайном Bootstrap на работающем кластере.

                        
systemctl is-active mariadb.service  # на каждой не-кандидатной ноде

                        
Проверка выполняется автоматически как шаг 1 Bootstrap Wizard и в endpoint POST /api/bootstrap. Отключить нельзя.

                    


                    

                        

                            
SST Progress Monitor (realtime)

                            Info
                        

                        
Модуль SstMonitor — автоматически активируется когда нода переходит в состояние Joiner / Joining / Donor/Desynced. Показывает progress bar для каждой такой ноды: процент передачи, метод SST (rsync / mariabackup), нода-донор, recv_queue. Polling каждые 3 сек через GET /api/node/{id}/sst-status. Автоматически скрывается после синхронизации.

                        
SstMonitor запускается и останавливается автоматически — вмешательства пользователя не требуется.

                    


                

            


            
            
            
            

                

                    
                    Мониторинг и метрики
                

                


                    

                        

                            
Обновить (кнопка в шапке)

                            Info
                        

                        
Принудительно запросить все wsrep-метрики со всех нод немедленно, не дожидаясь следующего авто-опроса. В режиме REAL + WebSocket данные и так приходят мгновенно — кнопка дополнительно отправляет HTTP-запрос для немедленного обновления. Частота авто-опроса настраивается в Настройках.

                        
SHOW GLOBAL STATUS LIKE 'wsrep_%';

                    


                    

                        

                            
wsrep_cluster_status

                            Metric
                        

                        
Primary — нормальная работа, кворум есть, запись разрешена. non-Primary — нода потеряла кворум, новые транзакции блокируются. Disconnected — нода вне кластера. В KPI отображается как «Cluster Status».

                        
SHOW STATUS LIKE 'wsrep_cluster_status';

                    


                    

                        

                            
wsrep_local_state_comment

                            Metric
                        

                        
Synced — нода синхронизирована, принимает чтение и запись. Donor/Desynced — нода отдаёт SST, временно медленнее. Joiner — нода получает SST (progress bar на карточке). Joined — получила SST, применяет IST-логи.

                        
SHOW STATUS LIKE 'wsrep_local_state_comment';

                    


                    

                        

                            
wsrep_flow_control_paused

                            Metric
                        

                        
Доля времени (0.0–1.0), когда репликация была приостановлена из-за отставания медленной ноды. 0.0 = норма. >0.1 = есть проблема с производительностью. >0.25 = серьёзное отставание, нужна диагностика. В KPI отображается как «FC Pause».

                        
SHOW STATUS LIKE 'wsrep_flow_control_paused';

                    


                    

                        

                            
wsrep_local_recv_queue

                            Metric
                        

                        
Размер очереди входящих транзакций репликации на ноде. 0 = нода не отстаёт. >0 = нода не успевает применять транзакции — причиной может быть высокая нагрузка на диск или CPU. Значение >5 требует внимания. В KPI показывается суммарно по всем нодам.

                        
SHOW STATUS LIKE 'wsrep_local_recv_queue';

                    


                    

                        

                            
wsrep_last_committed (Δ seqno)

                            Metric
                        

                        
Порядковый номер последней успешно применённой транзакции на ноде. Разница (Δ seqno) между нодами показывает отставание репликации в транзакциях. Отображается на странице «Диагностика» → блок «Репликация — Δ seqno» в виде сравнительных бар-чартов. Δ=0 = все в синхронизации.

                        
SHOW STATUS LIKE 'wsrep_last_committed';

                    


                    

                        

                            
wsrep_local_cert_failures

                            Metric
                        

                        
Количество транзакций, отклонённых при сертификации — то есть конфликты записи между нодами (optimistic concurrency control). Ненулевое значение означает что приложение пытается писать в одни и те же строки с разных нод одновременно. Отображается в KPI как «Cert Fail».

                        
SHOW STATUS LIKE 'wsrep_local_cert_failures';

                    


                    

                        

                            
wsrep_bf_aborts

                            Metric
                        

                        
Количество транзакций, принудительно прерванных Galera (Brute Force Abort) из-за конфликтов репликации. Транзакция с меньшим seqno откатывается автоматически. 0 = норма. >0 = конфликты записи, нагрузка на приложение. Отображается в KPI как «BF Aborts».

                        
SHOW STATUS LIKE 'wsrep_bf_aborts';

                    


                    

                        

                            
wsrep_cluster_size

                            Metric
                        

                        
Количество нод, которые в данный момент являются частью кластера (подключены и имеют кворум). Значение должно совпадать с числом нод в nodes.yaml + арбитр (если есть). Несоответствие означает что одна или несколько нод вышли из кластера.

                        
SHOW STATUS LIKE 'wsrep_cluster_size';

                    


                    

                        

                            
Event Log — Журнал событий

                            Info
                        

                        
Хронологический журнал всех действий и событий мониторинга. В режиме REAL: события с бекенда загружаются автоматически при старте (из /api/log), новые события приходят через WebSocket в реальном времени без перезагрузки страницы. Лог хранится в logs/galera-events.log. Кнопка «Экспорт лога» позволяет скачать полный лог-файл.

                        
В режиме MOCK лог хранится только в памяти браузера и сбрасывается при F5.

                    


                

            


            
            
            
            

                

                    
                    Диагностика
                

                


                    

                        

                            
Проверить всё

                            Action
                        

                        
Параллельная проверка SSH-доступности и подключения к MariaDB на всех нодах одновременно. Результат — таблица: нода, SSH ✓/✗, MariaDB ✓/✗, latency в мс, текущее wsrep-состояние. Отображает зелёный/красный хедер с общим итогом. Полезно при подозрении на проблему с сетью или сервисом.

                        
POST /api/diagnostics/check-all

                    


                    

                        

                            
Δ seqno — блок «Репликация»

                            Info
                        

                        
Визуальное сравнение wsrep_last_committed по всем нодам в виде горизонтальных баров. Нода с максимальным seqno — 100% зелёная, отстающие — со сдвигом и пометкой (−N). Обновляется автоматически вместе с циклом мониторинга. «Все ноды в синхронизации» = Δ=0.

                        
wsrep_last_committed (из мониторинга)

                    


                    

                        

                            
wsrep — сводная таблица

                            Info
                        

                        
Ключевые wsrep-переменные по всем нодам в виде матрицы «параметр × нода». Цветовая кодировка: зелёный = норма, жёлтый = внимание, красный = проблема. Параметры: cluster_status, cluster_size, connected, ready, state, last_committed, recv_queue, flow_control_paused, cert_failures, bf_aborts, wsrep_incoming_addresses (адреса нод), wsrep_gcomm_uuid (UUID группы), wsrep_protocol_version (версия протокола). Автообновление с циклом мониторинга.

                        
SHOW GLOBAL STATUS LIKE 'wsrep_%';

                    


                    

                        

                            
SHOW PROCESSLIST

                            Info
                        

                        
Список активных SQL-запросов на выбранной ноде: thread_id, пользователь, БД, команда, время выполнения (сек), статус, первые 100 символов SQL. Фильтрует системные потоки — показывает только клиентские запросы. Кнопка Kill для каждого запроса. Доступно в «Диагностика» → нода → Processlist.

                        
SHOW FULL PROCESSLIST;

                    


                    

                        

                            
Статус garbd

                            Info
                        

                        
Детальный статус Galera Arbitrator Daemon. Отображает: статус systemctl (active/failed), последние строки journalctl -u garbd с логом подключения к кластеру. Важно: garbd может быть active но не подключён к кластеру — именно поэтому нужен лог, а не просто статус. Доступно в «Диагностика» → секция «Garbd».

                        
systemctl is-active garbd && journalctl -u garbd --since "5 minutes ago"

                    


                    

                        

                            
Сравнение galera.cnf

                            Info
                        

                        
SSH-сбор ключевых параметров galera.cnf со всех нод и отображение в сравнительной таблице. Проверяет: wsrep_cluster_address, wsrep_sst_method, wsrep_provider, wsrep_node_address. Рассинхрон конфигов — частая причина проблем при добавлении новой ноды. Доступно в «Диагностика» → секция «Конфигурация».

                        
grep -E "wsrep_" /etc/mysql/mariadb.conf.d/galera.cnf

                    


                    

                        

                            
Ping (SSH) + Test Connection

                            Info
                        

                        
Комплексная проверка конкретной ноды: SSH ping (latency) + попытка подключения к MariaDB с реальными кредами из nodes.yaml. Результат показывает: SSH OK/FAIL + latency, DB OK/FAIL + сообщение об ошибке, текущее wsrep_local_state_comment. Доступно из кнопки «Test Connection» на карточке ноды.

                        
GET /api/node/{id}/test-connection

                    


                    

                        

                            
InnoDB Status — диагностика дедлоков

                            Info
                        

                        
Выполняет SHOW ENGINE INNODB STATUS на выбранной ноде через прямое SQL-подключение. Результат отображается в форматированном блоке с подсветкой секций: TRANSACTIONS (дедлоки), LATEST DETECTED DEADLOCK, SEMAPHORES (ожидания блокировок), FILE I/O. Незаменимо при расследовании проблем с производительностью. Доступно в «Диагностика» → InnoDB Status.

                        
SHOW ENGINE INNODB STATUS  →  GET /api/node/{id}/innodb-status

                        
Требует прямого SQL-подключения (db_user/db_password в nodes.yaml).

                    


                    

                        

                            
Disk / System Health

                            Info
                        

                        
Параллельная проверка системных ресурсов на всех нодах через SSH: дисковое пространство (df -h), оперативная память (free -h), uptime и load average. Результат — таблица с цветовой индикацией: диск >85% = красный, 70–85% = жёлтый, <70% = зелёный. Доступно в «Диагностика» → Системные ресурсы.

                        
POST /api/diagnostics/system-health  →  параллельный SSH df/free/uptime

                        
Работает при остановленной MariaDB. Полезно перед плановым обслуживанием и при диагностике нехватки места.

                    


                

            


            
            
            
            

                

                    
                    Режимы работы
                

                


                    

                        

                            
MOCK — тестовый режим

                            Safe
                        

                        
Симуляция кластера в браузере без обращения к бекенду. Данные генерируются JavaScript. Все кнопки работают, меняют состояние mock-нод. Режим для разработки, демонстрации и тестирования UI. Поддерживает сценарии: Normal, Node Down, Split Brain, SST, Flow Control. Сценарий восстанавливается после F5 из бекенда.

                        
В MOCK-режиме команды на серверы НЕ отправляются. Реальный кластер не затрагивается.

                    


                    

                        

                            
REAL — боевой режим

                            Danger
                        

                        
Подключение к реальному кластеру через бекенд FastAPI. Данные получаются из /api/status (wsrep-метрики через SSH+MySQL). Все команды (Start/Stop/Restart/Bootstrap) выполняются реально на серверах. В Real-режиме активен WebSocket для получения обновлений в реальном времени вместо HTTP-polling.

                        
⚠ Все действия в REAL-режиме выполняются на боевых серверах. Используйте осторожно.

                    


                    

                        

                            
Контур TEST / PROD

                            Warning
                        

                        
Визуальный переключатель для индикации рабочего окружения. TEST — обычный интерфейс. PROD — красный бейджик в шапке как предупреждение, что работа ведётся с боевой системой. Влияет только на отображение, не меняет API-эндпоинты.

                        
Переключение контура сохраняется в localStorage и восстанавливается при перезагрузке.

                    


                    

                        

                            
Сценарии Mock

                            Info
                        

                        
Симуляция различных ситуаций в MOCK-режиме через выпадающий список в шапке:

                            Normal — все ноды Synced

                            Node Down — одна нода упала, кластер в non-Primary

                            Split Brain — ноды разделились, нет кворума

                            SST in progress — одна нода в режиме Joiner/Donor

                            Flow Control — активный Flow Control на медленной ноде

                        
Текущий сценарий сохраняется в бекенде через POST /api/scenario и восстанавливается при F5.

                    


                

            


            
            
            
            

                

                    
                    Настройки и конфигурация
                

                


                    

                        

                            
Частота опроса

                            Info
                        

                        
Интервал автоматического обновления данных мониторинга. В режиме REAL + WebSocket: сервер сам присылает данные с этим интервалом через WS-соединение — нет лишних HTTP-запросов. В режиме MOCK: задаёт частоту setInterval-тика симуляции. Диапазон: 2–60 секунд. Сохраняется через /api/prefs.

                        
Малый интервал (<5 сек) увеличивает нагрузку на ноды при сборе wsrep-метрик через SSH+MySQL.

                    


                    

                        

                            
Добавить ноду

                            Action
                        

                        
Добавить новую ноду в файл nodes.yaml через форму: имя, IP/hostname, порт MariaDB (3306), SSH-порт (22), SSH-пользователь, путь к SSH-ключу. После добавления нода сразу появляется в мониторинге при следующем poll-цикле. Используйте «Reload nodes.yaml» для мгновенного применения без перезапуска бекенда.

                        
POST /api/config/node  (обновляет nodes.yaml)

                    


                    

                        

                            
Удалить ноду

                            Danger
                        

                        
Удалить ноду из nodes.yaml — нода перестанет мониториться. Физически нода из Galera-кластера не исключается (это делается через Stop + изменение wsrep_cluster_address на оставшихся нодах). Требует подтверждения. Действие применяется немедленно.

                        
DELETE /api/config/node/{id}  (обновляет nodes.yaml)

                        
После удаления нажмите «Reload nodes.yaml» для обновления конфигурации бекенда без перезапуска.

                    


                    

                        

                            
Reload nodes.yaml

                            Action
                        

                        
Перечитать конфигурационный файл nodes.yaml на бекенде без перезапуска сервиса. Применяет все изменения (добавленные/удалённые ноды, изменения арбитра, новые параметры SSH) немедленно. Эквивалентно kill -HUP для старых демонов, но работает через HTTP-запрос.

                        
POST /api/config/reload

                    


                    

                        

                            
Добавить / редактировать арбитр

                            Action
                        

                        
Настроить параметры Galera Arbitrator (garbd) в nodes.yaml: IP/hostname, SSH-порт, пользователь, ключ. Арбитр — лёгкий процесс без MariaDB, который обеспечивает кворум при 2 нодах данных. Статус арбитра отображается на дашборде и в «Диагностика → Garbd».

                        
Сохраняется в nodes.yaml → секция arbitrator:

                        
После изменения арбитра нажмите «Reload nodes.yaml» для применения.

                    


                    

                        

                            
Параметры подключения к БД

                            Action
                        

                        
Настроить глобальные параметры подключения к MariaDB: пользователь мониторинга и пароль. Эти параметры используются для сбора wsrep-метрик через SHOW STATUS. Сохраняются в nodes.yaml → секция db:. Рекомендуется создать отдельного пользователя только с правами REPLICATION CLIENT.

                        
CREATE USER 'monitor'@'%' IDENTIFIED BY 'pass';
GRANT REPLICATION CLIENT ON *.* TO 'monitor'@'%';

                    


                    

                        

                            
Предпросмотр nodes.yaml

                            Info
                        

                        
Отображает текущее содержимое файла nodes.yaml в реальном времени: имена нод, хосты, порты, SSH-параметры, настройки арбитра, параметры БД и poll_interval. Данные запрашиваются через GET /api/config — показывает реальное содержимое файла, а не кэш UI. Полезно для проверки корректности конфигурации.

                        
GET /api/config  → форматируется как YAML

                    


                    

                        

                            
Экспорт лога

                            Info
                        

                        
Скачать полный файл logs/galera-events.log с бекенда. Лог содержит все события с временными метками: изменения состояний нод, выполненные команды, ошибки подключения, результаты диагностики. Формат: текстовый, одна строка = одно событие. Полезно при разборе инцидентов.

                        
GET /api/log/download

                    


                    

                        

                            
Редактирование арбитра

                            Action
                        

                        
В разделе «Арбитры (garbd)» на странице Настройки кнопка Изменить открывает модальное окно с полями: ID, IP/Hostname, SSH Port, SSH User, SSH Key, DC. Изменения сохраняются через PUT /api/config/arbitrator/{arb_id} и отражаются в предпросмотре nodes.yaml немедленно.

                        
PUT /api/config/arbitrator/{arb_id}  {host, ssh_port, ssh_user, ssh_key, dc, id}

                        
Изменение ID арбитра обновляет запись на месте без пересоздания. Персистируется в nodes.yaml немедленно.

                    


                    

                        

                            
Валидация конфигурации (Pydantic)

                            Info
                        

                        
При загрузке nodes.yaml бекенд валидирует его через Pydantic-схему (ConfigSchema). Проверяются: обязательные поля (id, host), диапазоны портов (1–65535), типы данных. При ошибке — понятное сообщение: какое поле, какой узел, что неверно. Некорректный YAML возвращает 422 вместо 500.

                        
ConfigSchema(BaseModel)  →  NodeSchema, SettingsSchema, ArbitratorSchema

                        
Валидация выполняется автоматически при каждом вызове load_config(). Ошибки логируются и возвращаются клиенту.

                    


                

            


            
            
            
            

                

                    
                    WebSocket — обновления в реальном времени
                

                


                    

                        

                            
Индикатор WS (точка в шапке)

                            Info
                        

                        
Цветная точка рядом со временем обновления в шапке показывает статус WebSocket-соединения:

                            🟢 Зелёная — подключён, данные приходят в реальном времени

                            🟡 Жёлтая — идёт подключение / реконнект

                            🔴 Красная — ошибка / разрыв соединения

                            Время обновления показывает суффикс [WS] когда WS активен.

                        
Индикатор виден только в REAL-режиме. В MOCK-режиме WS не используется.

                    


                    

                        

                            
Авто-реконнект

                            Info
                        

                        
При разрыве WS-соединения фронтенд автоматически переподключается с экспоненциальной задержкой: 1с → 2с → 4с → 8с → ... → максимум 30 секунд. Пока WS переподключается — активируется HTTP-polling как fallback чтобы данные не устаревали. После восстановления WS polling снова останавливается.

                        
При частых реконнектах проверьте сетевое соединение до бекенда или увеличьте timeout в nginx/reverse-proxy.

                    


                    

                        

                            
Типы WS-сообщений

                            Info
                        

                        
Бекенд отправляет через WS два типа сообщений:

                            type: "status" — полный снапшот состояния кластера (все ноды, метрики, арбитр) — раз в poll_interval секунд

                            type: "event" — мгновенное уведомление о событии (нода упала, bootstrap завершён, ошибка) — отправляется сразу при возникновении

                            type: "pong" — ответ на heartbeat ping

                        
ws://host:8000/ws/cluster

                    


                    

                        

                            
Heartbeat / Ping

                            Info
                        

                        
Фронтенд отправляет текстовое сообщение "ping" каждые 20 секунд для поддержания WS-соединения активным (предотвращает таймаут через nginx/load balancer). Бекенд отвечает {"type":"pong"}. Если ответ не приходит — соединение считается разорванным и запускается реконнект.

                        
Для работы через nginx добавьте: proxy_read_timeout 86400; proxy_send_timeout 86400;

                    


                    

                        

                            
Rate Limiting — защита SSH-команд

                            Warning
                        

                        
Эндпоинт POST /api/node/{node_id}/action защищён in-memory rate limiter: максимум 10 SSH-команд за 60 секунд на одну ноду (per node_id). При превышении возвращается HTTP 429 Too Many Requests. Реализовано без внешних зависимостей — скользящее окно на collections.defaultdict + time.monotonic().

                        
HTTP 429: "Rate limit exceeded for node 'gc01': max 10 SSH actions per 60s"

                        
Лимит per node_id. Счётчик сбрасывается через скользящее окно автоматически — не требует перезапуска бекенда.

                    


                    

                        

                            
WebSocket Manager — Dependency Injection

                            Info
                        

                        
WebSocket Manager хранится в app.state.ws_manager (FastAPI lifespan) вместо глобальной переменной. Все эндпоинты получают его через request.app.state.ws_manager. Корректный lifecycle через async with lifespan, устранены глобальные side effects. asyncio.get_running_loop() вместо устаревшего get_event_loop() для Python 3.10+.

                        
app.state.ws_manager = _WsManager()  # в lifespan startup

                        
Паттерн соответствует FastAPI best practices.
